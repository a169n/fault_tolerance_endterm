1Introduction and relationship to the midterm

The midterm built a university platform (students, payments, transcripts, timetables) with software fault tolerance: retries with backoff, timeouts, a circuit breaker, health checks, idempotent payments, checkpoint and rollback, graceful degradation, replicas and a database standby. The endterm extends the same system, as the assignment requires, with four new layers: cloud/microservice resilience, observability with alerting, security with intrusion tolerance, and systematic verification by fault injection.

One codebase, three modes. Every container runs the same image; two switches select the behaviour. A measured difference between modes is therefore caused by the mechanisms, not by different code.
ModeSwitchesBehaviour
baselineFT=0 ENDTERM=0Same replicas and standby, but nothing uses them: no retries, timeouts, idempotency or security.
midtermFT=1 ENDTERM=0The midterm mechanisms S1–S10 and H1–H5, unchanged (tag midterm-final = commit 51100cf).
endtermFT=1 ENDTERM=1Midterm plus redundant gateways, outlier ejection, JWT authentication, authorization, validation, rate limiting and audit.

Monitoring (metrics, structured logs, correlation IDs, Prometheus, Grafana, alerts) and credential hygiene are on in all three modes, so all modes are measured the same way. Deploy with npm run up:baseline | up:midterm | up:endterm.

Assumptions. Crash, omission and timing faults (no Byzantine faults); one Docker host; synthetic data only; the host, Docker daemon and pinned images are trusted; secrets are generated per install into a git-ignored .env.

Threat model (STRIDE over five trust boundaries; full version in THREAT-MODEL.md). In scope: anonymous clients, students exceeding their rights, a stolen student token (limited by its 15-minute lifetime and the student's own rights), and faulty components. 16 containers on one Docker host. Blue boxes are new in the endterm.

Inherited from the midterm

  • Timeout 800 ms per attempt; up to 3 attempts (2 retries) with full-jitter exponential backoff (base 50 ms), each on the next replica.
  • Circuit breaker per pool: opens after 5 failures, half-opens after 5 s.
  • Health checks every 1 s take dead replicas out of rotation.
  • Idempotent payments (unique key) and a checkpoint + rollback sweep for interrupted payments (after 10 s).
  • Graceful degradation: a failed read is served from a stale cache (≤ 60 s old) as HTTP 203; reads fail over to the standby.
  • Restart policy (self-healing) and storage page checksums.

New in the endterm

  • Redundant gateways. nginx re-sends a failed request to the other gateway. This is safe only because every payment must carry a client Idempotency-Key (otherwise 400).
  • Outlier ejection. A replica with 3 consecutive failures leaves rotation for 10 s; never more than half a pool.
  • Liveness vs readiness. /health/live (process up) and /health/ready (dependencies up); Docker healthchecks every 2 s.
  • Auth outage degrades gracefully. Tokens are verified locally at the gateway, so an auth outage blocks only new logins.

Remaining single points of failure (accepted): nginx, the PostgreSQL primary (no automatic failover), auth-1, transcript-1, postgres-exporter (the only observer for DatabaseDown) and the host itself. In Kubernetes the same design maps to Deployments with liveness/readiness probes, a Service per pool and outlier detection in a service mesh (discussion only; not deployed).

4Monitoring, logging, metrics and alerting

Structured logs. Every service writes one JSON line per event with ts, svc, mode, kind, rid, level.

Correlation ID. The client's X-Request-ID (nginx generates one if it is missing; a service replaces an unsafe one with a fresh UUID) travels through nginx, the gateway and every service and appears in every log line and response. Hostile IDs (newlines, 10 KB, non-ASCII) are replaced, so they cannot inject into logs.

Metrics (Prometheus, scraped every 2 s): request count and latency histogram per route, upstream attempts by instance and outcome, instance up/ejected, breaker state, auth denials, rate-limited requests, and payments stuck in pending. Route labels use templates, not raw paths, so the number of series stays bounded.

Dashboard. One provisioned Grafana dashboard with 13 panels; OBSERVABILITY.md walks one real incident (E2) from alert to log lines by request ID.

Intrusion tolerance. The design assumes some attacks will get through a layer and limits the damage: a stolen token works only for 15 minutes and only within one student's rights; an attack burst is denied, counted and alerted (AuthFailureSpike); the database role cannot destroy data; a flood is cut by rate limits before it reaches the services; nginx failover cannot double-charge because of the client key.

Final review fixes (after the campaign): an idempotency key could be reused across students (now 409); a {param} route could reach a service's own /openapi.json; the stale cache kept 404s without a size bound; the app role could update user roles. Each fix has tests and was re-checked with one endterm run each of E5, E7 and E9.

7Fault-injection and security-test methodology

Each run lasts 70 s under a closed-loop workload of 10 clients (60 % student reads, 20 % transcripts, 20 % payments; 20 % of payments are re-sent with the same key). The fault is injected at +20 s and repaired at +45 s. Before every run the harness restores a known state: all containers healthy and replicating, chaos settings reset, payments truncated, balances zeroed, and no alert firing. Each run records every request (with its request ID), all service events, alerts (polled every 1 s), CPU and memory, and the payments table for key-level integrity checks.

9Discussion, limitations and lessons learned

Discussion. The endterm's measurable gains over the midterm are exactly where its new mechanisms act: killing a gateway no longer causes an outage, a slow replica no longer costs most of the throughput, and attacks turn from silent successes into denied, audited and alerted events. Everything the midterm already masked (crashes, node loss, interrupted payments) stays masked. The baseline shows why: without idempotency every client re-send became a second charge.

Limitations

  • One host: all 16 containers share CPU, disk and the Docker daemon; host failure is untested.
  • 3 repetitions: enough to see spread, not enough for significance tests.
  • Closed-loop workload flatters a system that hangs (fewer requests, fewer failures).
  • Some criteria do not discriminate between modes (E6 and E8 pass in the baseline; E3's whole-run p95; the ledger check cannot see double charges).
  • Detection and recovery times include window-close artefacts; per-operation recovery was derived afterwards from raw logs.
  • The campaign measured the code before the dependency upgrade and the final review fixes; those were checked with single repetitions, not a re-run.
  • Accepted risks: rate-limit state is per gateway (2× quota), no mTLS or public TLS, no token revocation, one shared DB role, containers run as root.

Lessons learned

  • Measure availability more than one way: request-based, time-based and goodput disagreed in E2, E3 and E7.
  • Check that the baseline fails a criterion before trusting it.
  • An "unexpected" alert is a finding: it exposed the timeout-nesting defect in E2.
  • Read raw data before believing an aggregate; the correlation ID made that fast.
  • Redundancy needs a safe retry contract: the nginx failover is safe only because the client sends the idempotency key.
  • Rate limits in a replicated tier must be sized for the whole cluster.

Next steps

Nest the timeouts (DB acquire < gateway attempt) and re-run E2; re-run the campaign on the upgraded dependencies; open-loop load for E3 and E6; shared rate-limit state; a second nginx and automatic DB failover; per-service DB roles and non-root containers.

10Conclusion and references

In 90 controlled runs the endterm passed all 10 scenarios in every repetition, against 6 for the midterm configuration and 2 for the baseline. It meets 9 of its 10 requirements (DR7 missed by one unexpected but genuine alert). Across the 60 midterm and endterm runs no payment was lost, duplicated or left pending. The weak points are reported with the data that shows them rather than tuned away.

★Defense cheat sheet: likely questions

Why three modes instead of comparing against the old midterm commit?

Same image, same host, same harness: the only variable is the switch, so a difference in the numbers is caused by the mechanisms. The old midterm campaign is quoted for reference only.

Why doesn't a failed gateway cause double charges when nginx re-sends the POST?

Every payment must carry a client-generated Idempotency-Key; a request without one gets 400. The database has a unique constraint on the key, so the re-sent request returns the stored payment instead of charging again. Across all 30 endterm runs: {{DUP_END}} duplicate charges.

What is the difference between the circuit breaker and outlier ejection?

The breaker is per pool: it stops calling a whole service that keeps failing. Ejection is per instance: it removes one bad replica after 3 consecutive failures for 10 s. A per-pool breaker cannot isolate one slow replica, because every successful retry on the healthy replica resets it (found in the midterm); ejection raised goodput from {{E3_MID}} to {{E3_END}} of normal.

Why does the baseline have higher availability than the endterm in E2?

Closed-loop clients: baseline requests hang without timeouts, so clients send almost nothing and record few failures ({{E2_RPS_BASE}} req/s served). The endterm fails writes fast and keeps serving reads ({{E2_RPS_END}} req/s). Time-based availability and goodput show the real picture.

How is an incident detected and diagnosed?

Detection: the first failed call is seen in under 1 s; the alert fires after the 2 s scrape and evaluation, its for period and, for rate rules, the window fill (6.0–10.3 s measured in the endterm). Diagnosis: the Grafana panels show which instance and which status; the request ID of a failed request finds every log line on every hop.

What happens if someone steals a student's token?

It expires within 15 minutes and only allows that student's own reads and payments. There is no revocation list; this is accepted risk R3.

Why can't alg:none or a forged token pass?

The verifier accepts only HS256 with the server's secret and checks issuer, audience and expiry; anything else raises an error and the gateway fails closed with 401. E9 tested all four token attacks: 36 × 401.

Does security slow the system down?

At normal load no overhead is visible. At the 110-client peak the p95 grew from about {{E6_P95_MID}} to {{E6_P95_END}} ms while throughput rose. Probably the per-request token, policy and limiter work, but the second gateway changed at the same time, so we cannot attribute it to security alone. It stays below the 1 s target.

Which requirement is not met, and why not fix the criterion?

DR7: HighLatencyP95 fired unexpectedly in E2. It is a real defect (the 1 s DB wait is longer than the 800 ms gateway timeout). Changing the acceptance rule after seeing the result would make the test meaningless, so it is reported as a miss and listed as the first next step.

How do you know the numbers are not made up?

Every table is generated by experiments/aggregate.ts from the 90 committed metrics.json files; the security counts and the incident timeline come from per-run metrics.json and the committed raw request and event logs. Re-running npm run campaign -- --reps 3 gives new measurements of the same kind, not identical numbers.

What would you do with more time?

Fix the timeout nesting, re-run the campaign on the upgraded dependencies, use an open-loop load generator, share rate-limit state between gateways, and remove the remaining single points of failure (second nginx, automatic DB failover).
